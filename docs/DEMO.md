# Demo Script

[← back to project overview](../README.md) · [docs index](../README.md#documentation)

A script for showing `tracker` to someone unfamiliar with it — a recruiter, a contributor, or a "why does this repo exist" skeptic.

## What to show first

Open the live [README.md](../README.md) on GitHub, not the code. The badges and the "As of {date}" snapshot make the point in five seconds: this is a live, self-updating data feed, not a static list someone forgot to update. Click through to [data/README.md](../data/README.md) second, to show the actual job table with working apply links.

## Step-by-step demo script

| Step | What to do | What to say |
|---|---|---|
| 1 | Open `README.md` on GitHub | "This whole page — every number, every badge — is generated by a script that runs automatically once an hour. Nobody typed these counts in by hand." |
| 2 | Point at the "Last updated" badge and `LAST_UPDATED` | "This timestamp updates every run. If you refresh this page an hour from now, it'll be different — and so will the job counts." |
| 3 | Click into [data/README.md](../data/README.md), scroll to a job row | "Every row links straight to the real employer application page — not a redirect, not an aggregator page. Click Apply, you land exactly where a manual search would've taken you." |
| 4 | Open the [Actions tab → Hourly Global Tech Roles PR](https://github.com/AhmedNassar7/tracker/actions/workflows/hourly-global-roles.yml) | "Here's the automation itself. It runs on a GitHub Actions cron schedule, no server anywhere. Each green run either found new data and opened+merged its own PR, or found nothing changed and did nothing — which is also correct behavior, not a failure." |
| 5 | Open a recent merged PR from that workflow | "Each of these PRs is one hourly snapshot. The PR history is basically a changelog of the job market as seen through this repo." |
| 6 | Open [scripts/fetch.py](../scripts/fetch.py), scroll to the `fetch_remotive` function | "The core of this is dead simple on purpose: fetch a source, normalize each row into one shared shape, filter it, done. No framework, no ORM, no database — just Python's standard library." |
| 7 | Open [config/companies_allowlist.yml](../config/companies_allowlist.yml) | "Anyone can widen or narrow which companies show up just by editing this YAML file — no code, no redeploy. It's picked up on the very next hourly run." |
| 8 | Run the pipeline live (see below) | "And you can run this exact pipeline on your own machine in under a minute, with zero setup." |

## Sample data to use during demo

Run these locally to generate real output on the spot rather than relying on a screenshot:

```bash
python scripts/fetch.py
python scripts/public_sources.py
python scripts/build_data_readme.py
```

If you want a guaranteed-fast, deterministic demo without waiting on 15 live network calls, use the existing test fixtures instead — `tests/test_fetch.py` already contains a realistic speedyapply-style markdown table and a Remotive-style JSON payload that exercise the parser without touching the network:

```bash
python tests/test_fetch.py
```

The ✅ output *is* a live demonstration of the parsing logic working correctly against real-shaped input from five different source formats in one run.

## The 3 most impressive things to highlight

1. **Zero infrastructure.** No database, no server, no paid API, no `requirements.txt` — the entire pipeline is Python standard library running on a free GitHub Actions runner. The "backend" is a cron job; the "frontend" is a Markdown file.
2. **Self-healing dead-link handling.** `check_url_alive()` doesn't naively trust a single HTTP check — it specifically works around a real bug class (ATS pages that mishandle `HEAD` but work fine on `GET`, observed live on Pinterest's careers page) so the published list never wrongly drops a live job over a flaky check. Point at the test that encodes this: `tests/test_fetch.py`'s "confirms a HEAD 404 with a GET before trusting it" case.
3. **Auto-discovery, not hardcoding.** The public layer doesn't ship a hardcoded company list for Greenhouse/Lever/Workday — it *derives* which boards to poll from whatever companies the curated layer already found, so coverage grows on its own as the allowlist grows, with zero config for those three platforms.

## Common questions someone would ask

**"Why not just use a database?"**
There's nothing to query beyond "give me the current list" — a flat JSON file committed to git *is* the database, and it comes with free version history, free hosting (GitHub itself), and zero ops.

**"How do you know a job posting is actually still open?"**
Two independent checks each run: (1) is the apply URL still alive (`check_url_alive`, GET-confirmed before declaring dead), and (2) is the posting still present in this run's fresh fetch from its source at all. Either failing moves it to `jobs-global-archive.json` with a `closed_at` timestamp.

**"What stops this from just re-posting garbage / spam companies?"**
The curated layer's `config/companies_allowlist.yml` gate — only companies on that list get published from the 10 curated sources, regardless of what those sources themselves list. The public layer's roles are separately filtered to actual software engineering titles via `is_software_job()`.

**"How often does this actually run, and does it ever silently break?"**
Hourly, via cron `"15 * * * *"`. It doesn't silently break: CI (`ci.yml`) runs the test suite on every change to the pipeline code before it can reach `main`, and each hourly run is a visible, individually inspectable GitHub Actions log plus (when something changed) a merged PR — a gap in that PR history is itself the signal something's wrong.

**"Can I add a company/source without knowing Python?"**
Yes for companies — `config/companies_allowlist.yml` and `config/extra_job_boards.yml` are plain YAML lists. Adding a brand-new source (a new website/API) does need a short Python fetcher function; see [DEVELOPER-GUIDE.md](DEVELOPER-GUIDE.md#add-a-new-curated-job-board-source).
