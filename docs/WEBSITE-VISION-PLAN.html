0Where we are today

The project already works and is genuinely useful. This plan builds on it — it does not restart it.

The pipeline

Pure Python stdlib, no deps. Two collector layers — curated (fetch.py, ~17 allowlisted sources) and public (public_sources.py, Greenhouse/Lever/Workday/Ashby/SmartRecruiters + hackathons/events). Merged at render time by build_data_readme.py into README.md, data/README.md, data/site-index.json, RSS feeds, and a 90-day stats-history.json. Runs hourly on GitHub Actions, auto-merges.

The site

Astro + React islands in site/, deployed separately, fetches site-index.json at runtime from jsDelivr (raw GitHub fallback) so data is ≤1h stale without redeploying. Pages: opportunities browser, global dashboard, personal application tracker (IndexedDB, local-first), resources. Tailwind, light/dark.

Just shipped (this work stream)

  • Closed-job detection: LinkedIn guest-API marker check, Apple / ByteDance soft-404 rules, upstream 🔒/strikethrough row skipping.
  • Coverage: Amazon pagination 3→10 pages; unknown-level Amazon roles kept (minus senior titles).
  • Formatting: scripts/company_names.py normaliser (Openai→OpenAI, Mongodb→MongoDB…); site shows New grad not new_grad.
  • Hackathons/events: closed ones dropped, soonest-deadline-first ordering, per-kind columns (no “Level” on non-jobs, “Deadline” column).

1North star

Three sentences to measure every feature against:

  1. Trust: if a listing is on the site, the apply link works and the role is really open. If we’re not sure, we don’t show it.
  2. Speed & clarity: a student on a slow connection finds a relevant, fresh role in under 30 seconds, on their phone, with no account.
  3. Habit: there’s a reason to come back tomorrow — new roles matched to me, a market story I want to follow, my own application funnel, a streak.

Success signals: GitHub stars, returning visitors, RSS/digest subscribers, “tracked applications” created, low bounce on the dashboard.

2Principles & guardrails non-negotiable

KeepWhy
No server, no database, no paid APIsThe whole project’s durability and $0 cost depend on it. Everything stays static files + GitHub Actions + a CDN. Personalisation is client-side only (IndexedDB/localStorage), same as the current application tracker.
No fabricated dataNever guess a value to fill a column. A field only one layer detects stays absent on the other. This already governs site-index.json and CompanyAvatar (initials, not a guessed logo).
Respect source termsUse official/JSON endpoints and public board APIs. No credentialed scraping, no circumventing bot protection at scale, no republishing content a source forbids. LinkedIn is used only via its own unauthenticated guest endpoint, read-only, low volume.
No PII collectionNo login, no email capture on-site. Digests are opt-in via RSS or a user-pasted webhook, not a stored list.
Generated files stay generatedAll human text lives in the generator. New site copy that must match the data goes through the same path.
Progressive enhancementCore list must render and be usable with no JS and on a 3G phone. Motion/animation is additive and respects prefers-reduced-motion.

5UX, motion & storytelling

Principle: motion clarifies, it never blocks. Everything here degrades to a clean static page and honours prefers-reduced-motion. Target: Lighthouse ≥ 95, no CLS, <100 KB JS on first view.

5.1 Structure — from “a table” to “a page with a spine”

  1. Hero / pulse. One line of live truth: “2,963 open roles · 189 added in the last 24h · updated 12 min ago”, a sparkline of the last 30 days from stats-history.json, and one primary action (“Find roles for me”). A quiet animated gradient / dot-field, paused on reduced-motion.
  2. The list stays the core and stays fast. Above it: a compact filter bar with result count; a “New since your last visit” toggle.
  3. Story strip between list and dashboard: 3–4 auto-generated cards — “Internships up 22% this month”, “Top hiring companies this week”, “Most roles: United States, then Germany” — each links into a pre-filtered list. Built from our own stats, screenshot-friendly.
  4. Dashboard as its own page (exists) — deepened in §7.
  5. Company mini-pages (/company/<slug>, static-generated): logo, role count over time, level/region breakdown, current roles. Pure derived data.

5.2 Micro-interactions & motion (the “feels alive” layer)

5.3 Craft details

  • Command palette (Cmd/Ctrl-K): jump to a company, apply a filter, open the dashboard, copy a shareable link. Keyboard-first.
  • Shareable state: every filter combination is already a URL — add “Copy link” + auto-generated OG image (static, per common filter) so shared links look good.
  • Density toggle: comfortable / compact rows.
  • Type & rhythm: one display face for headers (self-hosted, subset), system stack for body; consistent 4px spacing scale; a real focus-visible ring everywhere.
  • Iconography: one set (Lucide, tree-shaken), used consistently for kind/level/remote/region. Emoji only where the community boards’ vocabulary is the point (🔒 status, 🎓 PhD, 🛂 visa).
  • Accessibility: full keyboard nav, semantic table, ARIA on filter groups, contrast ≥ 4.5, reduced-motion honoured, screen-reader labels on every icon-only control.
  • PWA: it already ships a manifest + service worker — finish it: offline “last synced” view, installable, “add to home screen” nudge after the 3rd visit.

6Company logos next

The current CompanyAvatar deliberately renders initials because guessing a company’s domain for Clearbit-style logos risks showing the wrong company’s real logo — a fabrication. That reasoning still holds. The safe path:

  1. Maintain a hand-verified domain map (config/company_domains.yml) — only for allowlisted companies, checked the same way board tokens are.
  2. When a verified domain exists, render a logo from a stable provider; otherwise fall back to the initials avatar (never a guess).
  3. Provider: after Clearbit’s Logo API sunset (Dec 2025), the drop-in successor is Logo.dev (500K free req/mo, <img> by domain, SVG + dark-mode); Brandfetch is the quality alternative; Google’s s2/favicons is the zero-dependency last resort. Cache aggressively; lazy-load; fixed box to avoid CLS; onerror → initials.
  4. Store the resolved logo URL in site-index.json only when domain-verified, so the client does no guessing at runtime.

Licensing: these APIs serve third-party trademarks for identification (nominative use) — fine for a listing, but keep it to the verified allowlist and don’t restyle/recolour marks.

Refs: Post-Clearbit logo APIs (2026) · Logo API guide 2026 · logo.dev vs Brandfetch

7Personalisation & analytics

All client-side. No account, no server. Data lives in IndexedDB/localStorage (the tracker already does this) and is exportable (CSV/JSON, already implemented).

7.1 “For you” — the daily reason to return

  • Preferences (levels, regions, remote, company types, keywords, exclude-companies) stored locally; a one-screen setup, editable anytime.
  • Ranked feed: score each role client-side by preference match + freshness + (optional) company-type weight. “Why this matched” chips.
  • Seen / dismissed memory (Otta’s “never twice”): dismissed roles drop out; “new since last visit” uses the existing site-index.json checksum + a stored last-seen id set.
  • Saved searches: name a filter combo → pinned chips → each gets its own RSS URL (feeds are already generated; add per-preset ones) so “alerts” need no email list.
  • Weekly digest: a generated static “this week for <your prefs>” page + optional user-pasted Discord/Slack webhook the client posts to (their secret, never stored server-side).

7.2 Personal analytics — your own funnel

  • Deepen the tracker: counts and elapsed-time stats from statusHistory (median days applied→OA→interview→offer), response-rate by company type/level, a funnel chart, a calendar heatmap of activity, a streak.
  • “Compare to the market”: your applied-role mix vs the current dataset’s mix (all local).
  • Reminders (local notifications via the SW): “3 roles you bookmarked close in 48h”.

7.3 Market analytics — the public story

  • Expand stats-history.json dimensions: by level, region, country, company-type, source, remote-type — one snapshot/run, still bounded (90d).
  • Dashboard: trend lines, “fastest-growing companies this month”, “internship season curve”, region share, remote share over time, “time-to-fill proxy” (how long roles stay in the feed).
  • A monthly generated “State of Early-Career Tech Hiring” markdown post (in-repo, like the READMEs) — the kind of thing that gets shared and starred.

8System design & architecture

8.1 Keep the shape, tighten the seams

sources/*  ──►  collect  ──►  normalize  ──►  merge  ──►  emit
(fetchers)     (raw JSON)    (JobEntry/      (dedupe,   (README, data/README,
                             PublicEntry,     archive)   site-index.json, feeds,
                             patterns.py)                stats-history, OG images,
                                                         company mini-pages)
                                     │
                              validate (JSON Schema, config/*.schema.json)
  • Collector = Strategy pattern. Each source is a function returning normalized rows. Make the implicit contract explicit: a small Source dataclass (id, fetch(), kind, needs_verification) and a registry list, so adding a source is one entry and tests can enumerate them. (SOURCE_FETCHER_NAMES is already 90% of this.)
  • Liveness = Registry pattern. _SOFT_404_RULES (just generalised) is the model: URL-matcher → markers. LinkedIn handled by the same table shape. New sources add a rule, not a branch.
  • Normalization stays central in patterns.py + company_names.py so “level”/“region”/“role_type”/“company” mean one thing everywhere.
  • Emit = pure functions over the merged payload (build_site_index, update_stats_history, write_feeds already are). Add build_company_pages, build_story_cards, build_og_images the same way — each independently testable, each writing static files.

8.2 Data contracts & versioning

  • Every emitted file has a JSON Schema in config/ and is schema-checked at build (pattern exists). Add schema_version to site-index.json and have the site tolerate a mismatch gracefully.
  • The site depends only on site-index.json + stats-history.json shapes — keep that the one integration boundary. New UI features that need new fields add them there (absent-not-guessed rule applies).
  • Types mirrored by hand in site/src/lib/types.ts (convention already documented) — add a CI check that diffs the schema against the TS types.

8.3 Deployment

  • Two workflows stay decoupled: hourly data refresh (commits data) and site deploy (on site/ change). Site reads data at runtime from the CDN — unchanged.
  • Static generation additions (company pages, OG images, digest) run in the data workflow and are committed as files, so the site build stays trivial and fast.
  • Optional, only if ever needed: a single edge function for on-demand OG images. Not required for v1 — pre-generate the common ones.
